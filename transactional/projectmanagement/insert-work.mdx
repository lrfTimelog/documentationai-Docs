## How it works

For each WorkUnit: the employee is resolved from EmployeeInitials, the allocation of that employee on TaskID is looked up or created, and a registration is saved for the DATE part of StartDateTime with Duration as hours, Description as comment and AdditionalText. The registration then passes the normal time-registration rules. Work units with empty or unknown initials are dropped before saving and reported only as an Invalid message on the envelope. Failed items carry Status Error and, for most rules, only 'The time registration could not be saved.'. Billable: the flag follows the task's default; BillableDuration sets billable hours. No check is made that the caller may register time for the employee named in EmployeeInitials.

<ResponseField name="GUID" field-type="guid">
**Optional.**

<ResponseField name="TaskID" field-type="integer" required="true">
Integer ID of the task the time is registered on. The allocation of this employee on the task is looked up, or CREATED when missing.
</ResponseField>

<ResponseField name="EmployeeInitials" field-type="string" required="true">
Initials of the employee who owns the registration. On write, decides the owner and department of the registration.
</ResponseField>

<ResponseField name="Duration" field-type="duration" required="true">
PT1H30M). Stored as decimal hours.
</ResponseField>

<ResponseField name="StartDateTime" field-type="dateTime" required="true">
Only the DATE part is used: it is the registration's work date. The time of day is ignored on write; on read it is always 00:00.
</ResponseField>

<ResponseField name="Description" field-type="string">
**Optional.** The registration's comment.
</ResponseField>

<ResponseField name="AdditionalText" field-type="string">
**Optional.** The registration's additional text field.
</ResponseField>

<ResponseField name="BillableDuration" field-type="duration">
**Optional.** The billable part of the duration, stored as decimal billable hours; kept only when the registration is billable.
</ResponseField>

</Expandable>

</ResponseField>

## Errors

All errors come back with **HTTP 200**: check `ResponseState`, `ErrorCode` and `Messages`. The errors every operation can return (expired or invalid token, API not enabled, HTTPS required, general errors) are listed once in [Responses and errors](/transactional/guides/responses-and-errors#error-codes).

| ResponseState | ErrorCode | Message | What it means | What to do |
|---|---|---|---|---|
| Error | — | BatchContainer: Status Error, Message 'The time registration could not be saved.' (or the text of one violated rule) | Per item: a time-registration rule failed, or the GUID already exists. | — |
| Error | 40001 | Error during call on TimeLog.API, Message 'The current product doesn't allow this event' (or '... module is not active ...', '... feature is not active ...', '... user license doesn't allow this event') | Per item: the account / user licence does not allow creating time registrations. | Check the account's product / licence and the integration user's licence. |
| Invalid | 10002 | \{field\}, was null or empty | 'FirstName, was null or empty', 'Country, was null or empty'). | Send the named value. |
| Invalid | 30015 | Unknown employee Initials: '\{initials\}'. | Customer.KAM is not the initials of an existing employee. | — |
| Error | 40001 | Error during call on TimeLog.API, Message 'Silverlight tracker is stop supporting by TimeLog. Please use our latest Desktop Tracker.' | source = 8. | Send source = 0. |
| Invalid | 40004 | V1_\{n\} is deprecated. Please upgrade to V1_\{m\} or later. | Nothing is read or written and the token is NOT checked. | Call the same operation on the current version. |
| Error | — | — | Large batch inserts are the realistic trigger. | Split the batch into smaller requests. |
